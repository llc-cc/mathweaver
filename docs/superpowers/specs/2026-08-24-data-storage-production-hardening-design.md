# MathWeaver 数据存储生产加固设计

日期：2026-08-24
基线分支：`feat/oss-object-storage`

## 1. 背景与目标

当前 Web 部署已经使用 MySQL 保存学习数据，并能把任务文件同步到私有 OSS，但仍存在三类上线阻断问题：模型 API Key 明文保存并由设置接口返回；MySQL 与 OSS 采用覆盖式双写，失败时可能产生不一致；后端数据库、迁移、对象存储和容器缺少完整的持续验证门禁。

本次改造在不绑定特定云厂商服务的前提下完成以下目标：

1. 模型凭据在数据库中只以认证加密密文保存，浏览器永远不能取回完整 Key。
2. OSS 文件使用不可变版本和 manifest 管理，数据库只指向已完整校验的版本。
3. 删除、旧版本回收和异常协调通过数据库 outbox 实现幂等重试。
4. 历史列表不加载节点、边等大 JSON，并为容量、审计和监控建立生产边界。
5. 生产 Compose 对 OSS 和加密配置 fail closed，CI 覆盖迁移、MySQL、Fake OSS、镜像和健康检查。

真实 RDS 备份、OSS 版本控制、跨区域复制以及 RPO/RTO 演练属于部署验收，仓库提供检查工具和操作手册，但不以单元测试代替真实环境证据。

## 2. 范围与兼容边界

改造以 Web/MySQL 部署为主要安全边界。桌面兼容模式继续支持 SQLite 和本地文件，但设置 GET 同样只返回掩码，所有日志和序列化出口使用相同的敏感信息清洗规则。生产 Compose 必须使用 MySQL、OSS 和显式加密密钥；本地开发及自动化测试可继续使用本地对象存储。

现有 HTTP 路径保持不变。设置对象新增服务端生成的 `config_id` 和 `has_api_key`，保留现有名称、URL、模型及激活索引字段。旧客户端未携带 `config_id` 时只允许创建新配置；已有配置的空 Key 保留语义依赖 `config_id`，防止排序后把旧 Key 错配给另一配置。

本次不引入 KMS、消息队列或外部任务系统。加密和 outbox 均由仓库内模块实现，并保留将密钥提供器替换为 KMS 的接口边界。

## 3. 凭据安全

### 3.1 密钥配置与密文格式

新增独立的凭据加密模块，使用 `cryptography` 提供的 AES-256-GCM。每次加密生成 96 位随机 nonce，并使用 `user_id`、用途和密文版本组成 AAD，防止密文被复制到另一用户或另一字段后仍能解密。

生产环境通过后端 secret 文件提供：

- `MATHWEAVER_CREDENTIAL_KEYS_JSON`：`key_id` 到 32 字节 Base64 密钥的映射；
- `MATHWEAVER_CREDENTIAL_ACTIVE_KEY_ID`：新写入使用的密钥编号。

应用启动时校验 JSON、Base64 长度和 active key。生产模式缺少配置立即退出，不降级为明文。密文包含格式版本、`key_id`、nonce 和 ciphertext；读取可使用旧 key，写入始终使用 active key，从而支持滚动轮换。

### 3.2 数据模型与迁移

`user_settings` 增加 `llm_secrets_encrypted_json`，只保存按 `config_id` 组织的加密 secret map。`llm_configs_json` 只保存非敏感描述字段。兼容列 `llm_api_key` 在数据迁移成功后统一清空，后续写入保持空值。

Alembic 迁移只负责增加字段和约束；数据迁移命令在读取到生产密钥后逐行完成以下操作：

1. 从旧单配置列或完整配置 JSON 提取 Key；
2. 为配置补充稳定 `config_id`；
3. 加密 secret map；
4. 写入无 Key 的描述 JSON 和密文列；
5. 清空明文列，并在同一数据库事务中提交。

命令默认只报告待迁移数量，使用显式 `--apply` 才执行；可重复运行，已迁移行不会二次破坏。生产后端检测到残留明文时拒绝提供设置和任务执行，并输出不含明文的稳定错误。上线完成后必须轮换曾经明文保存的模型 Key；旧数据库备份无法由应用代码抹除。

### 3.3 API 与内部使用

公开 GET 返回 `api_key_masked` 和 `has_api_key`，不返回 `api_key`。掩码只表达“已配置”，不保留可用于猜测 Key 长度或前后缀的内容。

PUT 的规则为：

- 新配置必须提供非空 Key；
- 已有 `config_id` 的配置传空 Key 或省略 Key 时保留原值；
- 显式 `clear_api_key: true` 才删除已有 Key；
- 删除整个配置时一并删除其密文；
- 不接受客户端指定新的 `config_id` 覆盖其他配置。

Repository 提供两个读取入口：公开读取只产生脱敏 DTO；运行时读取才解密完整凭据。运行时对象只存在于进程内存，不写回任务快照、审计详情或导出文件。

### 3.4 敏感信息清洗

新增递归清洗器，识别大小写和常见变体下的 `api_key`、`embedding_api_key`、`authorization`、`token`、`password`、secret 及签名 URL 参数。日志、审计、任务事件、异常详情和 JSON 导出在边界处调用清洗器。SDK 原始异常不直接向 API、审计或普通日志透传，只映射成稳定错误码。

## 4. MySQL 与 OSS 一致性

### 4.1 不可变版本与 manifest

对象键改为：

`<prefix>/users/<user_id>/jobs/<job_id>/versions/<version_id>/...`

每次同步生成新的随机 `version_id`，不覆盖当前版本。同步过程先枚举受控本地目录，为每个文件生成相对路径、字节数和 SHA-256；随后上传文件并通过对象元信息或回读验证大小，最后写入 canonical JSON manifest。manifest 是版本的提交标记，包含 schema version、任务归属、版本号、创建时间、文件清单、文件总数和总字节数。数据库保存 canonical manifest 的 SHA-256。

任何缺少 manifest、归属不匹配、路径不安全、大小不一致或哈希错误的版本都不可恢复。

### 4.2 数据库状态

`history` 增加：

- `storage_version`：当前有效不可变版本；
- `storage_status`：`pending_upload`、`ready`、`delete_pending`、`storage_error`、`deleted`；
- `storage_checksum`：当前 manifest 的 SHA-256；
- `storage_file_count` 与 `storage_bytes`：容量与监控统计；
- `deleted_at`：软删除时间。

`object_storage_prefix` 暂时保留用于迁移旧数据，但新记录不再将可变任务前缀当作完整性依据。

上传并校验新版本后，Repository 在一个事务中切换当前版本和统计字段，并为旧版本写入回收 outbox。若事务失败，旧版本仍是唯一可见版本，新版本成为可安全扫描的孤儿，不会覆盖线上数据。

### 4.3 Outbox 与协调器

新增 `storage_outbox` 表，字段包含操作类型、任务与版本、状态、尝试次数、下次执行时间、租约、稳定错误码和时间戳。唯一幂等键防止同一清理操作重复创建。操作至少包括：

- `delete_job_versions`：软删除后的全部远端版本清理；
- `delete_version`：成功切换后回收旧版本；
- `delete_local_cache`：远端状态安全后清理本地缓存；
- `verify_version`：需要重新核验的版本。

专用存储 worker 从数据库领取到期任务，使用有限租约避免进程崩溃后永久占用，按指数退避重试。达到最大次数后进入 `failed`，保留稳定错误码供监控和人工重放。所有操作按目标版本幂等，重复删除“不存在”视为成功。

协调命令扫描四类异常：没有数据库引用且超过安全期的孤儿版本、数据库引用但不存在的版本、manifest 或文件校验失败、长期失败的 outbox。默认只读输出汇总；只有显式修复参数才创建 outbox 或变更状态，且不在扫描进程中直接批量删除对象。

### 4.4 删除与恢复

删除接口在同一数据库事务内设置 `deleted_at/storage_status=delete_pending` 并写 outbox。普通列表和详情立即隐藏软删除记录。worker 成功删除 OSS 版本及本地缓存后将状态置为 `deleted`；失败不恢复用户可见性，可继续重试和审计。

恢复时读取数据库指向的版本和 checksum，下载到受控临时目录，逐文件验证大小与 SHA-256。全部通过后，在任务锁内将现有目录移动为短期备份、安装新目录；任一步失败执行回滚并保留旧缓存。临时目录和备份目录由后续清理任务回收。恢复不能使用调用方提供的任意前缀或绝对路径。

## 5. 查询、容量、审计与监控

### 5.1 历史查询

`list_history` 使用显式列投影生成摘要 DTO，不实例化完整 `History`，不选择 `nodes_json`、`edges_json`、`source_markdown`、`source_pdf_json` 等大字段。详情查询维持归属过滤后按需加载完整数据。软删除条件进入所有普通查询。

### 5.2 容量边界

生产配置支持并校验以下上限：HTTP 上传字节、单任务文件数与文件总字节、节点数、边数、持久化历史 JSON 字节、单用户历史总字节、历史保留天数和最低可用磁盘字节。上传入口尽早检查请求大小，持久化前使用与 MySQL 相同编码计算 JSON 字节数，对超限返回稳定的 413、422 或 507。

部署预检查询 MySQL `max_allowed_packet`，若小于应用允许的最大持久化负载和安全余量则失败。保留期清理由协调命令创建可审计 outbox，不在 API 请求中执行批量物理删除。

### 5.3 安全审计

审计服务只接受预定义 action 和详情白名单。数据库变更类事件尽量与业务变更使用同一 Session 提交；登录失败等无业务事务事件单独写入。首批覆盖登录成功/失败、修改密码、管理员重置密码、用户启停、批量导入、设置变更、任务软删除和协调修复。

审计详情只记录主体、结果、数量、稳定原因码和必要请求上下文，不记录密码、临时密码、模型 Key、Token、完整配置、文件正文、签名 URL 或异常堆栈。审计写入失败时，安全敏感的管理变更回滚并返回稳定错误；登录失败审计不可反向暴露账号是否存在。

### 5.4 指标

后端提供仅容器网络可访问的 Prometheus 指标端点，公网 Nginx 不代理该路径。指标包括数据库事务失败计数、连接池占用、OSS 上传/恢复/删除失败、恢复耗时、outbox 各状态数量、孤儿和缺失版本数量、任务文件数及字节数。标签只使用低基数的操作和结果码，不包含用户、任务、对象键或异常文本。

## 6. 部署与 CI 门禁

生产 Compose 显式设置 `MATHWEAVER_OBJECT_STORAGE=oss`，后端启动时强制校验 OSS、MySQL 和凭据加密配置；开发和测试配置仍可选择 local。Compose 增加独立 storage worker 及健康检查，并保证 migration/data-migration 成功后才启动 API 和 worker。

新增后端质量工作流，至少执行：

1. Python 语法与项目静态检查；
2. 全部 pytest；
3. Alembic 离线 SQL 生成；
4. MySQL 服务上的迁移、关键读写和数据迁移集成测试；
5. Fake OSS 的上传故障、manifest 篡改、恢复中断、删除重试与协调测试；
6. TypeScript `tsc --noEmit`；
7. 前后端 Docker 镜像构建；
8. 测试配置下的容器启动和健康检查；
9. 静态断言生产 Compose 强制 OSS 且不向前端暴露 secret。

真实 OSS 不使用长期凭据接入公共 CI。发布前由部署人员在隔离前缀运行真实 OSS 验证脚本，并完成 RDS 备份恢复、行数核对、manifest checksum 与对象哈希抽检。

## 7. 错误处理与回滚

API 只返回稳定错误码和可操作提示。密钥解密失败、数据库提交失败、对象校验失败、容量不足和 outbox 失败分别处理，不用一个笼统 500 掩盖状态。任何错误文本进入日志前均清洗。

数据库迁移先增加可空兼容字段，再迁移数据，最后由应用切换读写；旧列暂不物理删除，便于应用版本回滚，但在成功迁移后必须为空。对象存储新版本与旧可变前缀并存时，读取优先数据库 `storage_version`；没有版本字段的旧记录通过一次性迁移/验证命令生成首个 manifest。确认无旧版本应用后再安排后续迁移删除兼容列与旧前缀。

## 8. 验证标准

自动化测试必须证明：

- 数据库和公开 API 中不存在明文 Key，空 Key 保留和显式清除语义正确；
- 密钥轮换可读取旧密文并用 active key 重写，错误密钥 fail closed；
- 日志、审计、任务 JSON 和导出均清除敏感字段；
- 上传任一阶段失败不会改变数据库当前版本，数据库提交失败不会破坏旧对象；
- manifest 缺失、越权、路径穿越、大小或哈希不符时恢复失败且旧缓存不变；
- 软删除与 outbox 同事务，重试和并发领取保持幂等；
- 历史列表生成的 SQL 不选择大 JSON 字段；
- 容量限制和 `max_allowed_packet` 预检能在提交前阻断；
- 生产配置缺失 OSS 或加密参数时拒绝启动；
- CI 构建的镜像可在测试配置下通过健康检查。

## 9. 已知限制与上线责任

AES 主密钥仍由部署环境负责保护；若 secret 文件与数据库同时泄露，应用层加密无法替代独立 KMS 的隔离能力。进程执行模型调用时必须在内存中短暂持有明文 Key，这是功能所需，但不得持久化或记录。

OSS 本身不提供跨多个对象的事务，设计通过不可变版本、manifest 提交标记和数据库指针把失败转化为可协调的孤儿对象。恢复时的本地目录切换受操作系统语义限制，通过任务锁、备份和回滚降低风险，但不是跨文件系统事务。

上线仍需部署人员提供真实 MySQL/OSS 凭据、加密主密钥、容量值和监控采集配置，并完成真实备份恢复及 RPO/RTO 演练。仓库交付会明确列出未能在本地或 CI 中完成的外部验证。
