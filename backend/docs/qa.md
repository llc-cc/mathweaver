# 组会讲稿与问答

## 1. 组会讲稿

### 开场版本

这周我主要想把工作重新收敛到我们的主线，也就是 `Node Logic Structure` 上。  
如果只看表面，这周做了两件事：一是修了一批之前自然语言节点里的问题，二是加了一个引用规则池。  
但我真正想讲的是，这两件事其实都在服务同一个目标，就是把我们的流程从“只会抽节点”推进到一个最小可运行的 `extraction-analysis-repair` 闭环。

### 第一部分：为什么这周先修自然语言节点问题

我先处理了之前自然语言节点里的一批问题，比如：

- LaTeX 冻结留下来的 `@@...@@` 占位符
- 多余反斜杠
- 一些标题太依赖原文局部上下文
- 重复标题导致节点区分度不够

这部分看起来比较工程，但其实是为主线打地基。  
因为如果节点本身都不可读、不稳定，那么后面的 analysis 和 repair 就没有可靠输入。

### 第二部分：为什么要做 `extract_references`

之前我们的 extraction 更偏向节点内部骨架，比如 context、conditions、conclusions。  
但数学文档里还有一类很关键的信息是在节点之间通过引用暴露出来的，比如：

- 根据定义 1 和定义 2
- 由命题 2 可知
- 上述定理
- 从式(1)和式(2)得

所以我这周单独加了一个 `extract_references` 阶段，用规则把这些引用信号从节点文本里提出来，并保存成结构化字段。

这一步的作用不是直接替代 relation extraction，而是先把“潜在依赖线索”显式化。

### 第三部分：怎么把它讲成 analysis，而不是只讲规则

如果只是抽到 `定义 2` 这几个字，其实还不够。  
真正关键的是，系统要知道：

- 它是不是一个依赖线索
- 如果没连上，是规则没识别到，还是锚点有问题
- 这个问题值不值得修

所以我把规则池输出成了 `reference_signals` 和 `repair_flags`。  
可以理解成先做一层很轻量的 analysis，把问题显式标出来。

高等代数里有个很典型的例子：  
有 7 个节点都在说“根据定义 1 和定义 2”，但是 `定义 2` 在文档里实际出现在更后面。  
所以原来系统会把这 7 次都打成 unresolved。  
这个时候问题就已经被分析清楚了：不是规则没看见，而是前向引用导致没法落锚。

### 第四部分：repair 这周补了什么

这周我没有再加新的 LLM，而是加了一个 `repair_lite`，专门处理两类高频、低风险的问题。

第一类是前向引用修复。  
如果一个 unresolved 的显式编号引用，在全文里能唯一定位到一个后文节点，那我就把它修成一个安全的 forward reference。

第二类是触发词降噪。  
像“由上述受到启发”“因此”“于是”这种表达，很多时候只是自然语言组织，不是真的在引用某个节点。  
如果没有更实质的 explicit 或 relative 信号，就不应该把它们都推进 repair 队列。

### 第五部分：这件事到底有没有帮助主线

我在高等代数样本上做了一个离线验证。  
repair 之前：

- unresolved explicit 有 8 个
- `trigger_without_target` 有 17 个
- 最终能接出来的显式规则边有 9 条

repair 之后：

- unresolved explicit 降到 1
- `trigger_without_target` 降到 1
- 显式规则边升到 16 条

也就是说，这个闭环已经不是概念上的，而是确实让节点间依赖结构更完整了。

### 收尾版本

所以我觉得这周最重要的进展不是“我又写了几个规则”，而是我们开始把 `Node Logic Structure` 做成一个真正能演化的流程：

- extraction 负责稳定抽骨架
- analysis 负责显式指出哪里有问题
- repair 先用规则把一批高频问题补起来

后面再往更强的节点内部逻辑致密化推进，比如定义依赖、条件作用域和逻辑缺口补全。

## 2. 导师可能会问的问题与参考回答

### Q1：你这个规则池是不是太 heuristic 了？

可以这样答：

是的，它本质上就是 heuristic，但这是有意为之。  
因为我们现在想先验证闭环有没有价值，而不是一上来就把所有问题都交给 LLM。  
这周优先落的是高频、可验证、低风险的问题，比如显式编号引用和前向引用修复。  
这些问题用规则做，结果可解释、成本低，也方便后面做 ablation。

### Q2：既然有 LLM analysis，为什么还要做规则？

可以这样答：

我理解这两层不是互斥，而是分工不同。  
规则层适合做稳定、低成本、强可解释的基础分析，比如显式引用、相对引用、触发词。  
LLM analysis 更适合处理边界歧义、隐式定义依赖、条件作用域这些更难的问题。  
这周我是先把规则型闭环跑通，作为 analysis-repair 的 v0。

### Q3：前向引用修复会不会误连？

可以这样答：

当前 repair_lite 只修一种比较保守的情况：  
全文中该 `(node_type, number)` 只能唯一匹配到一个后文节点。  
也就是说，不是所有后向 unresolved 都修，只修“唯一后文候选”的情况。  
像多候选、标题近似、语义模糊这种情况，我现在都没有自动修。

### Q4：那现在还没解决的核心问题是什么？

可以这样答：

现在还没解决的主要有三类：

1. 命名引用，比如 `Cauchy 不等式`，需要外部知识库或更强上下文。
2. 公式引用，比如 `式(1)`、`式(2)`，因为当前还没有公式级节点。
3. 真缺锚点问题，比如文本里写了 `命题 2`，但上游抽取出来的节点并没有稳定保留这个 label。

所以这周的定位不是“全做完”，而是先把最容易验证的一段闭环做出来。

### Q5：这和你们的“逻辑致密化”到底怎么接？

可以这样答：

我觉得这周做的是逻辑致密化里最基础的一块，就是先把节点间显式依赖补齐。  
因为如果连“这个节点引用了哪个定义/命题”都不稳定，后面做节点内部的逻辑补全会缺上下文。  
所以我的想法是先把 document-level dependence skeleton 立起来，再往节点内部的 boundary/gap/definition analysis 推。

### Q6：怎么评价你这周的工作，不只是看几个案例？

可以这样答：

我现在已经有一个小的离线评测口径：

- unresolved explicit 数量
- `trigger_without_target` 噪声数量
- 最终显式规则边数量

在高等代数样本上这三个指标都有改善。  
后面我会把这套统计固定成统一评测脚本，再扩展到更多文档。

### Q7：如果导师追问“创新点在哪里”

可以这样答：

我觉得创新点不在某一条正则，而在整体范式：

1. 不是只抽 theorem skeleton，而是做 node-level logic structure。
2. 不是只做 extraction，而是强调 extraction-analysis-repair 的闭环。
3. 在单文档场景里，把文档级引用、符号表、默认上下文都看成结构恢复的一部分，而不是孤立处理单个节点。

这也是为什么我会把本周的引用规则池和 repair_lite 都包装到主线里，而不是当成单独修 bug。
