# 形式化实验问题分析与修改方案草案

**依据材料**:

- `实验报告1_方式1vs方式2_形式化语义对比.md`
- `实验报告2_round2_20260419.md`
- `实验报告3_代数学引论_测试5.md`

**目标**: 从三轮实验中提炼稳定问题，并提出一组可以在当前代码中逐步实现、不过拟合具体测试集、且能体现数学结构思想的修改方案。

---

## 一、核心结论

三轮实验的共同结论是：M2（完整 JSON 上下文）整体优于 M1（仅 statement），但优势不是压倒性的。M2 在编译成功率和复杂命题理解上更稳定，尤其对标准基、最小公倍数、变量背景较多的命题有帮助；但 M2 也更容易被标题、标签或无关上下文干扰，生成过度复杂或逻辑偏移的形式化结果。

因此，后续不应简单选择“只用 M1”或“只用 M2”，而应改为**双路候选 + 数学结构约束 + 轻量验证筛选**。也就是说，M1 提供简洁基线，M2 提供上下文增强，再用一套与领域无关的数学结构规则判断哪一个更接近原命题。

从错误分布看，当前主要瓶颈已经不是 Lean 语法编译，而是语义保真。线性代数实验中编译成功率普遍在 90% 以上，代数学引论测试中 M2 达到 100% 编译成功；但严格语义正确率仍在约 60%-75% 区间。这说明继续只优化 prompt 或编译修复的收益有限，真正需要加强的是从自然语言到数学逻辑结构的中间表示。

## 二、问题分析结果

### 2.1 M1 与 M2 的差异

M1 的典型优势是简洁、干扰少、结构不容易膨胀。它在简单定义、直接命题、局部公式表达上更稳，不容易引入多余变量和复杂构造。

M1 的典型问题是上下文不足，容易过度泛化或选错数学对象。例如把“子集对数乘封闭”上升为完整子空间定义，把向量组秩误写为矩阵秩，或者在变量角色不清时出现除数与被除数顺序颠倒。

M2 的典型优势是能利用标题、类型、标签、标准化形式和主题信息，对复杂命题、定义性对象和上下文依赖更强的条目表现更好。例如标准基需要同时表达线性无关和张成，M2 更容易保留完整结构。

M2 的典型问题是上下文噪声。标题中的“极大线性无关组”等词可能诱导模型引入不必要的极大性构造；完整 JSON 中的附加字段也可能使模型生成恒真式、复杂 Finset/Matrix 包装，甚至混淆 `Fin n` 与 `Fin s`。

### 2.2 稳定错误类型

**变量角色错误**是跨领域稳定出现的问题。代数学中“b 是 a 的因子”对应 `b ∣ a`，但模型容易把参数顺序写反；线性代数中也有 `s≤n`、`s≤r` 等变量含义混淆。这类错误本质上不是语法问题，而是自然语言角色没有绑定到形式化变量。

**逻辑连接词错误**也非常稳定。实验中多次出现用 `→` 表达例子中的并列事实，或用蕴含替代等价、用恒等式替代等价关系。典型如“例如”类命题应使用 `∧` 汇总同时成立的性质，而不是写成条件推出结论。

**数学概念降级或替换**是语义偏差的重要来源。不可约元定义中题目使用相伴关系 `~`，模型却用 `IsUnit` 替代；最大公因子定义中题目要求“满足最大性的因子”谓词，模型却直接调用 `GCDMonoid.gcd` 实现函数。这说明当前系统缺少“题目要求定义什么”和“Mathlib 里已有实现是什么”之间的边界判断。

**API 选择不符合数学语境**在向量组秩问题中反复出现。`Matrix.rank` 与 `Module.rank (Submodule.span ...)` 在某些例子中数值等价，但前者表达矩阵秩，后者表达向量组生成子空间的维数。语义正确性评估不能只看是否有可能等价，还要看是否保留原命题所处的数学对象。

**过度添加条件**主要出现在 M2。比如公倍数定义中添加题目未要求的非零条件，最大公因子定义中添加正性或非零约束，素元相关命题中显式要求 `a≠0`。这类错误会让命题从原题变成更强或更弱的版本。

**结构性复合命题丢失**常见于“充分必要条件 + 推论”“定义 + 性质”“一组等价关系”这类节点。模型可能只形式化第一层内容，漏掉后续推论；或者把多个子命题强行合并成一个 iff，改变原有逻辑结构。

**数据质量问题**仍然会传导到形式化阶段。线性代数实验中的 OCR 错误“获相等”应为“秩相等”，导致命题本身无意义。此类问题无法靠 formalizer 单独解决，需要上游 OCR/文本修复或异常检测。

### 2.3 评估指标暴露的问题

GTED 当前用于比较 M1 与 M2 的结构相似度，而不是与标准答案的相似度。因此 GTED 高不代表正确，GTED 低也不一定错误。测试5中有些条目 M1/M2 结构极像但都错，例如不可约元定义都把相伴关系降级为单位性；也有些条目 GTED 很低但都语义正确，说明不同形式化路径可以等价表达同一命题。

这提示后续评估不能只做字符串或 token 层相似度，而应转向**数学对象、变量角色、逻辑骨架、关键谓词**的结构比较。

## 三、可在代码中逐步实现的修改方案

### 3.1 方案 A：双路候选与自适应选择

**思路**: 保留 M1 和 M2 两种生成方式，但不提前固定使用哪一个。对每个节点同时生成两个候选，然后用规则和轻量模型判断哪个更符合原题。

**为什么不过拟合**: 这不是针对某条数据写补丁，而是承认“简洁输入”和“完整上下文”各有适用区间，把选择问题显式化。

**可实现改动**:

1. 在 formalizer 批处理层增加 `candidate_mode = statement | full_json | dual`。
2. `dual` 模式下保存两个候选的 Lean 代码、编译结果、prompt 摘要和结构特征。
3. 增加候选选择器 `FormalizationCandidateSelector`，先用硬规则过滤编译失败，再按语义保真分数排序。

**初始选择规则**:

- 若一个候选编译失败，优先选择另一个。
- 若题目是简单定义且 M2 引入额外非零、正性、极大性条件，优先 M1。
- 若题目包含标题依赖、标准对象、复合定义、上下文变量，优先 M2。
- 若两个候选都通过，比较逻辑骨架和关键谓词覆盖率。

### 3.2 方案 B：变量角色绑定器

**思路**: 在生成 Lean 前，先从自然语言中抽取“角色表”，明确每个变量在命题中的语义位置。例如 `b 是 a 的因子` 应绑定为 `divisor = b`、`dividend = a`；“向量组含 s 个向量”应绑定为 `cardinality = s`，不要误用空间维数 `n` 或秩 `r`。

**数学味道**: 这相当于给命题建立一个小型的 typed context，把自然语言变量先映射到数学角色，再映射到 Lean 参数。

**可实现改动**:

1. 新增 `role_binding` 中间字段，作为 formalizer 输入的一部分。
2. 在数学消歧或 formalizer 前增加轻量规则：
   - `x 是 y 的因子` -> `x ∣ y`
   - `y 被 x 整除` -> `x ∣ y`
   - `x 是 y 的倍数` -> `y ∣ x`
   - `向量组的秩` -> `rank(span(vector_family))`
   - `含有 s 个向量` -> cardinality，不等同于 ambient dimension
3. 在 prompt 中要求模型先遵守 `role_binding`，再生成 Lean。

**优先覆盖案例**:

- 整除、因子、倍数、公因子、公倍数、最大公因子、最小公倍数。
- 向量组个数、空间维数、秩、极大线性无关组。

### 3.3 方案 C：逻辑骨架抽取与一致性检查

**思路**: 在 formalizer 前或后，为每个命题抽取一个轻量逻辑骨架，例如：

```text
definition: Def(name, params, iff/body)
equivalence: A ↔ B
example: A ∧ B ∧ C
implication: hypotheses -> conclusion
chain: N_i ⊆ N_{i+1}
multi_part: [claim_1, claim_2, corollary]
```

然后检查生成的 Lean 是否保留了同样的逻辑外形。

**为什么有创新性**: 这不是单纯 prompt engineering，而是引入“自然语言命题的逻辑骨架”作为中间表示。它贴近数学书写的真实结构，也能和后续 GTED/ASSESS 类结构评测衔接。

**可实现改动**:

1. 在 analysis 阶段或 formalizer 前增加 `statement_skeleton` 字段。
2. 对常见触发词做规则抽取：
   - “当且仅当”“充分必要条件” -> `iff`
   - “例如”“取”“于是” -> `example_conjunction`
   - “若/如果/则” -> `implication`
   - “定义为/称为” -> `definition`
   - “进一步/并且/此外/推论” -> `multi_part`
   - `⊆`、`包含于` -> non-strict inclusion
   - `⊂`、`真包含` -> strict inclusion
3. 生成后对 Lean 代码做粗粒度检查：
   - 原题是 example，不应只有 `→`。
   - 原题是 iff，不应只有单向 `→`。
   - 原题是 definition，不应直接退化为已有函数调用。
   - 原题是 non-strict chain，不应使用 `<`。

### 3.4 方案 D：数学概念保真词典

**思路**: 建立一个小而可扩展的“概念保真词典”，记录自然语言概念、推荐 Lean 表达、禁止替换、适用语境。

**示例条目**:

```yaml
associated:
  cn: ["相伴", "相伴关系", "~"]
  prefer: "Associated"
  avoid_as_replacement: ["IsUnit"]
  note: "Associated a b 表示二者相差一个单位，不能简化为某一项是单位。"

vector_family_rank:
  cn: ["向量组的秩", "向量组秩"]
  prefer: "Module.rank K (Submodule.span K ...)"
  avoid_as_default: ["Matrix.rank"]
  note: "Matrix.rank 只在题目明确给出矩阵时作为首选。"

gcd_definition:
  cn: ["最大公因子", "最大公约数"]
  prefer_when_defining: "d ∣ a ∧ d ∣ b ∧ ∀ c, c ∣ a → c ∣ b → c ∣ d"
  avoid_when_defining: ["GCDMonoid.gcd"]
  note: "题目要求定义时优先谓词化，不直接调用实现函数。"
```

**可实现改动**:

1. 新增 `backend/pipeline/stages/math_disambiguation/concept_lexicon.py` 或配置文件。
2. 在 formalizer prompt 构造时，根据节点关键词注入少量相关概念规则。
3. 在候选选择器中，如果 Lean 输出触发 `avoid`，降低该候选分数。

**优点**:

- 词典是领域知识，不是样本补丁。
- 可以逐步扩展：线性代数、抽象代数、群论、拓扑等都能加各自概念。
- 能解释错误原因，便于报告和人工审核。

### 3.5 方案 E：定义与实现分离检查

**思路**: 当原题是“定义某概念”时，Lean 输出应尽量给出该概念的谓词结构，而不是直接调用 Mathlib 已封装函数。调用已有函数可以作为后续定理使用，但不应替代定义本身。

**可实现改动**:

1. 若节点类型是 `def` 或文本包含“称为”“定义为”，增加 `definition_mode = true`。
2. 在 prompt 中加入约束：定义类节点优先展开条件，不要直接调用封装好的同名函数。
3. 后处理检查：
   - `最大公因子` 定义若只出现 `gcd` 而没有共同因子和最大性结构，标记为语义风险。
   - `最小公倍数` 定义若只出现 `lcm` 而没有公倍数和最小性结构，标记为语义风险。
   - `不可约元` 定义若出现 `IsUnit` 但没有 `Associated`，标记为概念缺失。

### 3.6 方案 F：上下文降噪与字段加权

**思路**: M2 不应把完整 JSON 原样交给模型，而应按字段可信度和任务相关性重排。`statement/content/original_form` 应高权重，标题和标签只作为辅助，不允许覆盖正文。

**可实现改动**:

1. 将 M2 prompt 改成分层输入：
   - `Primary statement`: 必须忠实形式化。
   - `Auxiliary context`: 只用于消歧，不得引入正文没有的条件。
   - `Do-not-overfit hints`: 标题只帮助识别主题，不代表额外假设。
2. 对容易干扰的字段设置截断或摘要：
   - 标题只保留概念词，不直接作为命题内容。
   - 标签只用于命名，不用于构造数学条件。
3. 增加“新增条件检查”：如果输出中出现原题没有的非零、正性、极大性、有限性条件，标记为风险。

### 3.7 方案 G：OCR/文本异常的数学一致性预警

**思路**: 对明显不符合数学语义的文本做预警，而不是直接送入 formalizer。比如“获相等的两个向量组”应被识别为疑似 OCR 错误。

**可实现改动**:

1. 建立低成本异常规则：
   - 数学关键词前后出现罕见动词或错字，如“获相等”。
   - 命题缺少谓词中心，例如只有对象没有关系。
   - 标题和正文核心概念冲突，如标题含“秩”，正文无 rank/维数相关表达。
2. 对异常节点输出 `needs_text_repair = true`。
3. 对这类节点先调用文本修复/人工确认/多候选 OCR 对齐，再进入 formalizer。

### 3.8 方案 H：结构化评估升级

**思路**: 当前 GTED 应从“M1 vs M2 相似度”升级为“候选 vs 原题结构约束”的评估。短期可以不用完整 Lean 语义等价证明，先做轻量结构分数。

**建议分数项**:

- `compile_score`: 是否编译通过。
- `skeleton_score`: 是否保留 iff/implication/conjunction/definition/chain 等逻辑骨架。
- `role_score`: 除数、被除数、变量个数、维数、秩等角色是否一致。
- `concept_score`: 是否保留相伴、向量组秩、最大性、最小性等关键概念。
- `extra_condition_penalty`: 是否添加原题没有的条件。
- `api_context_score`: API 是否符合数学对象语境。

**候选总分草案**:

```text
score = 0.30 * compile_score
      + 0.25 * skeleton_score
      + 0.20 * concept_score
      + 0.15 * role_score
      + 0.10 * api_context_score
      - extra_condition_penalty
```

这个分数不追求一步到位替代人工语义判断，而是先用于候选排序、风险标记和实验对比。

## 四、推荐实施优先级

### 第一阶段：低成本、高收益

1. 修改 M2 prompt 的上下文字段结构，明确正文优先、标题辅助、禁止引入额外条件。
2. 增加逻辑骨架规则，优先覆盖 `iff`、`example_conjunction`、`definition`、`non_strict_chain`。
3. 增加概念保真词典的第一批条目：相伴关系、向量组秩、矩阵秩、gcd/lcm 定义、严格/非严格包含。
4. 在后处理中加入风险标签，不直接改 Lean 输出，先用于报告和人工复核。

### 第二阶段：双路候选选择

1. 批处理支持 M1/M2 同时生成。
2. 保存两个候选的结构特征。
3. 实现候选选择器，先用规则分数选择更优结果。
4. 在原三组实验上回放，比较“Best-of-M1/M2 + selector”是否超过单独 M1/M2。

### 第三阶段：数学结构评估

1. 用 Lean LSP hover 或 AST 信息提取关键谓词与类型。
2. 将 GTED 从 token/tree 相似度扩展为概念级结构相似。
3. 引入“结构风险报告”，自动解释为什么某条形式化可能语义不保真。

## 五、预期效果与实验设计

建议以现有三组实验作为固定回归集，但不要把规则只写死在这些样本上。每次修改后记录以下指标：

1. 编译成功率。
2. 严格语义正确率。
3. 风险标签召回率：已知错误是否被标出。
4. 风险标签误报率：正确结果是否被过度标风险。
5. M1/M2/Selector 三者对比：Selector 是否能在 M1 和 M2 各自优势案例中选到正确候选。

理想的第一阶段目标不是立刻把语义正确率提高到 90%，而是先做到：

- 对变量角色错误、逻辑连接词错误、概念替换错误有稳定预警。
- 对 M2 过度添加条件有明显抑制。
- 对定义类节点不再轻易用 Mathlib 实现函数替代题目定义。
- 对 OCR 异常节点不再盲目进入形式化阶段。

## 六、可以包装成创新点的表述

本项目的改进重点可以表述为：面向数学教材自动形式化的**逻辑致密化与语义保真中间层**。与只做 prompt 的 autoformalization 不同，该方法不直接从自然语言跳到 Lean，而是在中间显式维护：

1. 变量角色表：解决除数/被除数、向量个数/空间维数/秩等角色错配。
2. 逻辑骨架：保留定义、蕴含、等价、例子、链式包含、多子命题结构。
3. 概念保真词典：防止相伴关系、向量组秩、最大/最小性等数学概念被 API 或近义表达替换。
4. 双路候选选择：利用 M1 的简洁性和 M2 的上下文性，同时用结构评估抑制二者各自缺陷。
5. 文档级上下文约束：把符号表、章节默认假设、局部定义环境作为受控上下文，而不是无差别拼入 prompt。

这个方向既能解释当前实验中的错误，也能自然连接后续“单文档证明蓝图”“逻辑致密化”“依赖关系提取”和“结构化评估”。
