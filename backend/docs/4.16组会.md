## 2. 规则池：`extract_references` 做了什么

对应实现说明见：[extract_references.md](./extract_references.md)

### 2.1 我们为什么要加这一层

单靠节点骨架抽取，只能知道“这个节点内部写了什么”；
但在数学文档里，很多真正的逻辑依赖是通过引用显式暴露出来的，比如：

- `根据定义 1 和定义 2`
- `由命题 2 可知`
- `上述定理`
- `由式(2)`

因此我们单独加了一个 `extract_references` 阶段，专门从节点文本中提取引用信号，并输出到 `reference_signals`。

### 2.2 当前支持的规则类型

| 规则类型 | 作用 | 示例 | 
|---|---|---|
| 显式编号引用 | 定位定义/定理/命题等节点依赖 | `根据定义 1 和定义 2` | 
| 中英别名映射 | 统一 `定理 2` / `Theorem 2` | `Theorem 2` | 
| 相对引用 | 定位最近前文节点 | `上述定理` | 
| 公式引用 | 记录公式层依赖线索 | `从式(1)和式(2)得` | 
| 命名引用 | 记录人名定理/不等式 | `由 Cauchy 不等式` |
| 触发词 | 捕捉潜在的依赖/推导线索 | `根据` / `由` / `因此` | 

### 2.3 规则样本分析

#### 样本 A：显式编号引用识别成功

```text
根据定义 1 和定义 2,几何空间中,共面的三个向量是线性相关的.
```

对应识别结果：

- `定义 1 -> label_exact -> node 0`
- `定义 2 -> ...`

这说明规则层已经能把“显式依赖”先抓出来，后面就可以再判断为什么没法落锚。

#### 样本 B：英文别名引用识别

```text
由式(2)及 Theorem 2 知...
```

对应识别结果：

- `Theorem 2 -> 定理 2 -> node 1`
- `式(2)` 被记录为 formula reference

这说明中英标签映射已经打通。

#### 样本 C：相对引用识别成功

```text
根据定义1和定理 2，由 Cauchy 不等式，上述定理给出...
```

对应识别结果：

- `定义1 -> node 0`
- `定理 2 -> node 1`
- `上述定理 -> relative_nearest_previous -> node 1`

这说明我们不仅能抓显式编号，也能抓“最近前文同类型节点”的相对引用。

#### 样本 D：公式引用被记录但暂不解析


```text
由已知条件 s < r, 因此方程组 (2) 必有非零解 ... 则从式(1)和式(2)得
```

当前处理：

- 会记录 `式(1)`、`式(2)` 到 `formula_references`
- 但不会直接解析成节点级边

原因是：当前节点粒度不是公式节点，强行解析容易误连。

#### 样本 E：命名引用被记录

```text
由 Cauchy 不等式...
```

当前处理：

- 能识别为 `named_references`
- 暂不落到具体节点

原因是：这类引用需要外部知识库或更强上下文，目前先把信号保留下来。

## 3. 从 extraction 到 analysis：我们识别出了什么问题

### 3.1 之前的问题：只抽出来，不知道哪里“不完整”

之前即使抽到了节点，也很难系统回答这些问题：

- 这个节点是不是在引用上文定义，但没接出来？
- 这个引用没接出来，是规则没识别到，还是锚点丢了？
- 这是一个真问题，还是只是“由/因此”这种语言噪声？

### 3.2 这周新增的轻量分析信号

在 `extract_references` 里，我们把这些信息显式化成了：

- `explicit_targets`
- `relative_references`
- `formula_references`
- `named_references`
- `reference_triggers`
- `repair_flags`

这一步可以理解为：先把“潜在问题”显式标记出来，给后面的修复阶段消费。

### 3.3 典型问题：触发词噪声

真实样本，来自高等代数：

```text
由上述受到启发,我们引出一个概念...
```

这里的 `由` 只是自然语言连接词，不是真正的“根据某个节点”。

如果不做分析，系统会把它也丢进待修复队列，造成大量噪声。


## 其他轻量修复点

这部分是从 [现存问题.md](./现存问题.md) 里挑出来、能直接落代码的一批问题。共同原则是：

- 不新增 LLM 环节
- 尽量前移到 extraction 附近解决
- 修复结果继续进入后续 analysis / relations，而不是只做展示层清洗

### 修复 1：上游缺失 label 的保守补回

修复阶段：

- `extract_statements`

解决问题：

- 节点已经抽出来，但 `label` 因“编号和公式/正文粘连”丢失

真实样本：

```text
定义 $1{K}^{n}$ 中向量组 ...
定义 $2{K}^{n}$ 中向量组 ...
```

### 5.1 主线不是“多做一个规则池”，而是让节点结构更可用
离线结果：

```text
label_repair_count=3
label_repair key=7 label=定义 repaired1
label_repair key=8 label=定义 repaired2
```

这一步的意义是：把前面节点重新变成可引用锚点，否则后面的 `extract_references` 再强也只能 unresolved。

### 5.2 修复 2：子命题编号保留

修复阶段：

- `split_nodes`

解决问题：

- 像 `Proposition 1.5` 这种含 `(a)(b)(c)` 的复合命题，原先拆开后所有子节点都只有同一个裸 `label`

```text
设 G 是可解群，π 是素数集合。(a) H 是 Hall π-子群。
设 G 是可解群，π 是素数集合。(b) K 是 Hall π-子群。
```

当前结果：

```text
split_enrich 0 label=Proposition 1.5(a) label_suffix=a
split_enrich 1 label=Proposition 1.5(b) label_suffix=b
```

这意味着后续关系构建不再只能落到一个模糊的 `Proposition 1.5`，而能区分具体子结论。

### 5.3 修复 3：同组子命题的共享背景抽取

修复阶段：

- `split_nodes`

解决问题：

- 全局背景在每个子命题里重复，既浪费 token，也不利于恢复“系列命题”的结构


```text
设 G 是可解群，π 是素数集合。(a) H 是 Hall π-子群。
设 G 是可解群，π 是素数集合。(b) K 是 Hall π-子群。
```

当前结果：

```text
shared_context=设 G 是可解群，π 是素数集合。
local_content=(a) H 是 Hall π-子群。
```

这一步的意义是：节点不再只是一堆被扁平化复制的文本，而开始保留“共享前提 + 局部结论”的结构。

### 5.4 修复 4：`statement_form` 后验纠偏

修复阶段：

- `extract_logic_tuples`

解决问题：

- `equivalence` 常被误压成 `implication`
- `equality / formula` 常被误归到默认类型

```text
A 当且仅当 B
f(x) = g(x)
```

当前结果：

```text
statement_form_repair 0 before=implication after=equivalence
statement_form_repair 1 before=implication after=equality
```

利用规则，比如出现“当且仅当”“iff”“equivalent to”这类词，就优先判成 equivalence

这一步的意义是：后续分析里“条件-结论边界”会更稳，不会一开始就把等价关系压扁。

### 5.5 修复 5：归一化白名单，保护数学命名空间

修复阶段：

- `common/node.py` 的变量归一化

解决问题：

- 一些高频数学记号会在 normalize 时被拆坏，典型就是 `Ind`、`Hom` 这类命名空间

```text
Ind_H^G \chi = Hom(V,W)
```

当前结果：

```text
normalize_whitelist=Ind_H^G \chi = Hom(V,W)
```

这说明这类数学构造在归一化后不会再被错误改写成破碎 token，后面做依赖或分析时保真度更高。

## 这和主线 `Node Logic Structure` 有什么关系

### 主线不是“多做一个规则池”，而是让节点结构更可用

如果只做 extraction，我们得到的是：

- 节点骨架
- 但依赖不完整
- 噪声很多
- 无法稳定服务“单文档证明蓝图”

加入 analysis + repair 之后，节点结构开始具备三种能力：

1. 知道自己依赖了谁
2. 知道哪些依赖目前有问题
3. 能自动修一部分高价值、低风险的问题

### 对“逻辑致密化”的意义

`创新点ver1.0` 里提到的主线是：

- 变量范围缺失
- 隐式定义依赖
- 局部条件作用域
- 中间推理省略
- 复合对象缺失

本周的 `extract_references + repair_lite` 主要先覆盖了其中最容易落地的一块：

- **隐式定义依赖 / 显式引用依赖**

也就是说，我们先把“节点间的显式依赖骨架”做出来，再往节点内部的 boundary/gap/definition analysis 扩展。

### 目前要诚实说明的一点

现在真正接成闭环的是：

- `extraction`
- `reference-based lightweight analysis`
- `rule-based repair`

而 `analysis/stage.py` 那套更强的 LLM 分析层虽然已经有模板和字段，但本周没有大改接进实际 repair。

所以可以把这周定位成：

> 我们先把闭环做出一个工程上可跑的 v0 版本，优先解决高频、可验证、低风险的问题。
