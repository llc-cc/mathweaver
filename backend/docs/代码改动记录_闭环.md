# 代码改动记录：本周 extraction-analysis-repair 闭环

## 1. 本周改动目标

围绕 `Node Logic Structure` 主线，把当前工程从“只有 extraction”推进到一个轻量可运行的闭环：

- extraction：继续稳定节点骨架与文档级引用信号抽取
- analysis：把引用问题显式标成结构化信号
- repair：增加不依赖新 LLM 的 `repair_lite`

---

## 2. 新增/修改文件

### 2.1 新增 `repair_lite` stage

新增文件：

- [repair_lite/stage.py](../pipeline/stages/repair_lite/stage.py)
- [repair_lite/__init__.py](../pipeline/stages/repair_lite/__init__.py)

功能：

1. 对 `extract_references` 产生的 unresolved 显式引用做轻量修复
2. 对明显的 `trigger_without_target` 噪声做抑制
3. 输出 `repair_lite_report.json`

当前已实现的修复策略：

- `forward_reference_repair`
- `suppress_trigger_without_target`

### 2.2 修改 orchestrator

修改文件：

- [orchestrator.py](../pipeline/orchestrator.py)

改动：

- 在 `extract_references_stage.run(...)` 后接入 `repair_lite_stage.run(...)`

当前顺序变为：

1. `extract_logic_tuples`
2. `analysis`（可选）
3. `extract_references`
4. `repair_lite`
5. `build_relations`

### 2.3 修改 `build_relations`

修改文件：

- [build_relations/stage.py](../pipeline/stages/build_relations/stage.py)

改动：

- `extract_explicit_relations(...)` 原先只接受 `resolved_index < 当前节点`

目的：

- 让 `repair_lite` 修出来的 `forward_label_exact` / `forward_label_normalized` 也能进入显式规则边

### 2.4 新增测试脚本

新增文件：

- [test_extract_references.py](../scripts/test_extract_references.py)
- [test_extract_references_unit.py](../scripts/test_extract_references_unit.py)

- 离线验证 `extract_statements` 阶段丢失的 label 能否从原始块文本中补回

### 2.5 修改 `extract_statements`

修改文件：

- [extract_statements/stage.py](../pipeline/stages/extract_statements/stage.py)

改动：

- 新增 `repair_missing_labels_from_problem_dict(...)`
- 在 `extract_nonempty_blocks(...)` 之后、写出 `unsplit_statement_dict.json` 之前执行

目的：

- 修复节点已经抽出、但 `label` 因原始文本格式粘连而丢失的情况
- 当前主要兜底样式为：
  - `定义 $1{K}^{n}$ ...`
  - `定义 $2{K}^{n}$ ...`

这一步是对上游节点锚点的保守修复，不涉及新的 LLM 调用

### 2.6 修改 `split_nodes`

修改文件：

- [split_nodes/stage.py](../pipeline/stages/split_nodes/stage.py)

改动：

- 新增 `enrich_split_blocks(...)`
- 在 `extract_nonempty_blocks(...)` 之后补充拆分后节点的结构字段

当前新增字段：

- `shared_context`
- `local_content`
- `parent_label`
- `label_suffix`
- `sibling_group_size`
- `sibling_index`

目的：

- 保留 `(a)(b)(c)` 这类子命题编号
- 从同组子节点中抽取公共背景，减少扁平化复制

### 2.7 修改 `extract_logic_tuples`

修改文件：

- [extract_logic_tuples/stage.py](../pipeline/stages/extract_logic_tuples/stage.py)

改动：

- 新增 `repair_statement_forms(...)`
- 在 `merge_mixed_node_dict(...)` 之后对 `statement_form` 做后验规则纠偏

当前支持的保守修复：

- `当且仅当 / iff / if and only if` -> `equivalence`
- 单纯等式表达式 -> `equality`
- 空类型或 `other` -> 回退 `implication`

同时保留：

- `statement_form_before_repair`
- `statement_form_repair`

### 2.8 修改变量归一化

修改文件：

- [node.py](../pipeline/common/node.py)

改动：

- 给 `normalize_text_with_variables(...)` 增加白名单保护
- 从“单词级保护”扩展到“常见数学记号级保护”

当前保护的高频前缀包括：

- `Ind`
- `Res`
- `Hom`
- `Aut`
- `End`
- `Ext`
- `Tor`
- `Sylow`

目的：

- 避免 `Ind_H^G`、`Hom(V,W)` 这类命名空间在归一化过程中被拆坏

### 4.3 代表性真实样本

#### 样本 0：问题定位到 `extract_statements`

原始 `md` 中前半段确实存在：

```text
定义 1 ...
定义 2 ...
根据定义 1 和定义 2 ...
```

但在 `unsplit_statement_dict.json` 中，对应的两个定义节点已经变成：

- `node_type=定义`
- `label=""`

说明：

- 问题不是节点没抽出来
- 而是上游 `extract_statements` 没把这两个定义的编号保住

根因：

- 原始缓存文本更接近 `定义 $1{K}^{n}$ ...`
- 编号和公式/正文粘连，导致保守的 label 提取规则没有识别成功

#### 样本 0-修复结果：上游 label 补回

来自 [label_repair_test.log](../test_output/高等代数-丘维声-上册-第三章节选/_stage_cache/logs/label_repair_test.log)：

```text

key=7 node_type=定义 label='定义 1'
key=8 node_type=定义 label='定义 2'
```

这说明当前加的 `label repair` 至少能把这个高代样本里的关键缺失锚点补回来。

#### 样本 0-补充：五个轻量修复点的统一验证

来自 [lightweight_repairs_test.log](../test_output/高等代数-丘维声-上册-第三章节选/_stage_cache/logs/lightweight_repairs_test.log)：

```text

split_enrich 1 label=Proposition 1.5(b) label_suffix=b shared_context=设 G 是可解群，π 是素数集合。 local_content=(b) K 是 Hall π-子群。
```

说明：

- `label repair` 已经能补回真实样本里丢失的定义编号
- `split_nodes` 已经能保留子序号并抽出共享背景
- `statement_form` 已经能对等价 / 等式场景做后验纠偏
- 归一化白名单已经能保护高频数学命名空间

其中：

- `label repair` 使用真实高代样本
- `split_enrich` / `statement_form_repair` / `normalize_whitelist` 当前为合成验证，后续需要继续补真实样本覆盖

#### 样本 1：前向引用修复

文本：

```text
根据定义 1 和定义 2,几何空间中,共面的三个向量是线性相关的.
```

修复前：

- `定义 1 -> label_exact`
- `定义 2 -> unresolved`

修复后：

- `定义 2 -> forward_label_exact -> node 20`

#### 样本 1-补充：重复编号锚点问题

真实样本统计：

- `定义 1` 出现 2 次
- `命题 1` 出现 3 次

说明：

- 这份样本里不是“多个定义 2”
- 真正暴露出来的问题是：同一本书内重复编号已经存在，不能只靠裸 `label`

因此这次代码里增加了：

- `title/context + label` 的组合 alias
- 重复编号时优先取最近前文，而不是一律取第一个

具体例子：

- 节点 `26` 中引用 `命题 1`
- 候选节点是 `[7, 24, 25]`
- 当前解析结果为最近前文 `node 25`

#### 样本 2：触发词降噪

文本：

```text
由上述受到启发,我们引出一个概念...
```

修复前：

- 只有 `由` 被识别成 trigger
- 被打上 `trigger_without_target`

修复后：

- 保留 trigger 信号
- 但从 repair 队列中移除该噪声 flag

#### 样本 3：仍未修复的反例

文本：

```text
由命题 2 可知...
```

当前状态：

- 仍 unresolved

原因：

- 当前抽出来的节点中没有稳定可定位的 `命题 2` 锚点

说明：

- `repair_lite` 当前只修“能唯一确认的安全问题”
- 不做语义猜测式修复

## 5. 这次改动的意义

### 5.1 对主线的意义

这次不是简单增加几条规则，而是把主线往闭环推进了一步：

- extraction 不再只输出节点骨架
- analysis 开始有结构化问题信号
- repair 已经可以消费这些信号并修出真实收益

### 5.2 当前边界

这次有意保持轻量，没有做的包括：

- 新的 LLM repair 环节
- 命名引用实体对齐
- 公式级节点构造
- 多跳引用链修复
- 文档级全局假设传播
- 复杂符号多义解析

所以这次更适合定位成：

> 一个规则驱动、可解释、可评测的 repair v0
